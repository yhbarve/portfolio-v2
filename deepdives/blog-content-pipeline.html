How the Blog Works

This portfolio uses Markdown files as the source of truth, Contentlayer as the build-time content compiler, and a Next.js App Router page to render each post.

The Short Version

1. You write a Markdown file in blogs/, such as blogs/nextjs-and-md.md.
2. Contentlayer reads it using contentlayer.config.ts. The config says that every **/*.md file under blogs is a Post.
3. Contentlayer generates data in .contentlayer/generated, including typed exports like allPosts and per-post JSON files.
4. Next.js imports allPosts in the writings list and in src/app/blog/[slug]/page.tsx.
5. The blog page renders prebuilt HTML by placing post.body.html into the page with dangerouslySetInnerHTML.

Where the Markdown Lives

Blog posts are plain Markdown files in the root-level blogs/ directory. Each file starts with frontmatter, which is the metadata between the opening and closing --- lines. 

---
title: "Building a Markdown Blog with Next.js and Contentlayer"
date: "2025-08-15"
summary: "..."
tags: ["nextjs", "markdown", "contentlayer"]
published: true
author: "Yash Barve"
category: "Build"
coverImage: "/blog/markdown-blog.jpg"
---

## Introduction

Markdown content starts here.

Contentlayer separates that file into two broad pieces: frontmatter fields like title, date, summary, and tags, plus the Markdown body that becomes HTML.

How Contentlayer Knows What to Read

The important setup is in contentlayer.config.ts. The project defines one document type named Post: 

export const Post = defineDocumentType(() => ({
  name: "Post",
  filePathPattern: `**/*.md`,
  contentType: "markdown",
  fields: {
    title: { type: "string", required: true },
    date: { type: "date", required: true },
    summary: { type: "string" },
    published: { type: "boolean", default: true },
    tags: { type: "list", of: { type: "string" } },
    author: { type: "string" },
    category: { type: "string" },
    coverImage: { type: "string" },
  },
  computedFields: {
    slug: {
      type: "string",
      resolve: (doc) => doc._raw.flattenedPath,
    },
  },
}))

The makeSource call points Contentlayer at blogs. That means the pattern **/*.md is evaluated inside the blogs/ directory, not across the whole repository. 

export default makeSource({
  contentDirPath: "blogs",
  documentTypes: [Post],
})

The computed slug comes from doc._raw.flattenedPath. For example, blogs/nextjs-and-md.md becomes the slug nextjs-and-md, which maps to the URL /blog/nextjs-and-md.

How Markdown Becomes HTML

Contentlayer runs the Markdown body through a unified Markdown pipeline. In this project, that pipeline is customized with remark and rehype plugins: 

markdown: {
  remarkPlugins: [remarkGfm, remarkMath],
  rehypePlugins: [
    rehypeSlug,
    [rehypeAutolinkHeadings, { behavior: "wrap" }],
    [rehypeExternalLinks, { target: "_blank", rel: ["noopener", "noreferrer"] }],
    rehypeKatex,
    [rehypePrettyCode, { theme: "github-dark" }],
  ],
}

The remark plugins operate while the content is still Markdown. remark-gfm adds GitHub-flavored Markdown features like tables and task lists, while remark-math understands math syntax. The rehype plugins operate after Markdown has become an HTML tree. They add heading IDs, wrap headings with anchor links, make external links open in a new tab, render math with KaTeX, and syntax-highlight code blocks.

The generated JSON shows the result clearly. A post gets a body.raw field with the original Markdown body and a body.html field with the final HTML string. 

{
  "title": "Building a Markdown Blog with Next.js and Contentlayer",
  "date": "2025-08-15T00:00:00.000Z",
  "body": {
    "raw": "\\n## Introduction\\n\\nFor my very first...",
    "html": "<h2 id=\\"introduction\\"><a href=\\"#introduction\\">Introduction</a></h2>..."
  },
  "slug": "nextjs-and-md"
}

What Next.js Imports

Contentlayer generates TypeScript definitions and data exports under .contentlayer/generated. The key export is allPosts, typed as an array of Post objects. 

export declare const allPosts: Post[]

The generated Post type includes the metadata fields and the compiled Markdown body: 

export type Post = {
  title: string
  date: IsoDateTimeString
  summary?: string
  published: boolean
  tags?: string[]
  category?: string
  coverImage?: string
  body: Markdown
  slug: string
}

How the Writings List Works

The writings page imports allPosts, filters out unpublished posts, optionally filters by category, sorts newest first, and links each row to /blog/{slug}. 

const posts = allPosts
  .filter((p) => p.published)
  .filter((p) => {
    if (!categoryFilter) return true;
    return p.category === categoryFilter;
  })
  .sort((a, b) => +new Date(b.date) - +new Date(a.date));

The homepage writings section does a similar thing, but only shows the five newest published posts.

How an Individual Blog Page Works

The route src/app/blog/[slug]/page.tsx is the dynamic route for individual posts. It uses the generated slugs to tell Next.js which static pages can be built: 

export const generateStaticParams = () =>
  allPosts.map((p) => ({ slug: p.slug }));

When someone visits /blog/nextjs-and-md, the page reads the route param, finds the matching post in allPosts, and returns a 404 if no post exists. 

const { slug } = await params;
const post = allPosts.find((p) => p.slug === slug);
if (!post) return notFound();

The page then renders the title, summary, date, optional cover image, and finally the compiled HTML: 

<div
  id="blog-content"
  className="prose prose-base md:prose-lg ..."
  dangerouslySetInnerHTML={{ __html: post.body.html }}
/>

The prose classes come from Tailwind Typography. They do not convert Markdown to HTML. They style the already-generated HTML tags, such as <h2>, <p>, <ul>, <pre>, and <table>.

Why dangerouslySetInnerHTML Is Used

By the time the page renders, Contentlayer has already produced a trusted HTML string from local Markdown files in the repository. React normally escapes strings, so rendering post.body.html directly would show the HTML as text. The dangerouslySetInnerHTML prop tells React to insert that string as real DOM nodes.

This is reasonable here because the content is local, version-controlled Markdown. If the HTML came from arbitrary user input, it would need a much stricter sanitization story.

How the Table of Contents Works

The page also renders ContentTimeline beside the article on large screens. That component runs in the browser, finds h2 and h3 elements inside #blog-content, and builds a list of anchor links from their generated IDs. Those IDs exist because rehype-slug added them during the Contentlayer compile step.

The Full Pipeline

  1. Add or edit a Markdown file in blogs/.
  2. Run the app or build. The Next config wraps the app with withContentlayer.
  3. Contentlayer reads files matching **/*.md under blogs/.
  4. Frontmatter is validated against the Post schema.
  5. The filename becomes the computed slug.
  6. The Markdown body is converted into an HTML string using the configured plugins.
  7. Generated data and types are written into .contentlayer/generated.
  8. Next.js imports allPosts for listing pages and blog detail pages.
  9. The detail page finds the matching post by slug.
  10. The rendered article injects post.body.html and styles it with Tailwind Typography.

Key Takeaway

The blog is not reading Markdown from disk at request time. The Markdown is compiled at development/build time into typed JavaScript data and pre-rendered HTML. The runtime page is mostly doing lookup and presentation: find the post by slug, render metadata, inject the compiled HTML, and let Tailwind style the resulting elements.
